Git Notes for a New Software Engineer

Read top to bottom once, then use the cheat sheet at the end. Every command here is something you will use at work.

1. The mental model

Git is a distributed version control system. It stores your project as a series of snapshots (commits), not as file diffs. Every developer has a full copy of the history locally, and a remote (GitHub, GitLab, Bitbucket) is just another copy everyone agrees to sync with.

Git vs GitHub: Git is the tool on your machine. GitHub is a website that hosts Git repos and adds pull requests, issues, and CI.

The three areas

Working directory  --git add-->  Staging area (index)  --git commit-->  Repository (.git)
   (your files)                  (what the next commit                  (permanent history)
                                  will contain)
  • Working directory: the files you edit.
  • Staging area: a draft of your next commit. This lets you commit only part of your changes.
  • Repository: the committed history, stored in the hidden .git folder.

File states

Untracked (new, Git ignores it) -> Tracked & unmodified -> Modified -> Staged -> Committed.

Key vocabulary

  • Commit: a snapshot with an ID (SHA hash), author, message, and pointer to its parent.
  • Branch: a lightweight movable pointer to a commit. Creating branches is nearly free.
  • HEAD: pointer to where you are now (usually the tip of your current branch).
  • origin: the default name for the remote you cloned from.
  • upstream branch: the remote branch your local branch tracks (e.g. origin/main).

2. One-time setup

git config --global user.name "Your Name"
git config --global user.email "you@company.com"   # use the email tied to your GitHub account
git config --global init.defaultBranch main
git config --global core.editor "code --wait"       # VS Code as editor (optional)
git config --global pull.rebase false               # or true; ask your team's convention
git config --list                                   # verify

Authentication: use SSH keys or a personal access token / credential manager. Passwords no longer work for GitHub over HTTPS.

ssh-keygen -t ed25519 -C "you@company.com"   # then add ~/.ssh/id_ed25519.pub to GitHub
ssh -T git@github.com                         # test the connection

3. Starting a repo

git init                      # turn current folder into a repo
git clone <url>               # copy a remote repo (creates folder, sets origin)
git clone <url> my-folder     # clone into a specific folder name

4. The everyday cycle

git status                    # what changed? what is staged? (run this constantly)
git add file.js               # stage one file
git add src/                  # stage a folder
git add .                     # stage everything in the current directory
git add -p                    # stage interactively, hunk by hunk (great habit)
git commit -m "Add login form validation"
git commit                    # opens editor for a longer message
git commit -am "msg"          # stage + commit all TRACKED files (skips new files)

Looking at changes

git diff                      # unstaged changes
git diff --staged             # staged changes (what the next commit contains)
git diff main..feature        # difference between two branches
git show <commit>             # details and diff of one commit

Looking at history

git log                       # full history
git log --oneline             # one line per commit
git log --oneline --graph --all --decorate    # visual branch graph
git log -p file.js            # history of one file with diffs
git log --author="Name"
git log --since="2 weeks ago"
git blame file.js             # who last changed each line (use it to find context, not to blame people)

Good commit messages

  • Imperative mood, under ~50 chars for the subject: Fix null check in user service, not fixed stuff.
  • Blank line, then an optional body explaining why (the diff already shows what).
  • One logical change per commit. If you need "and" in the message, consider two commits.
  • Many teams use conventional prefixes: feat:, fix:, docs:, refactor:, test:, chore:.

5. Branching and merging

git branch                    # list local branches (* = current)
git branch -a                 # include remote branches
git switch -c feature/login   # create AND switch (older syntax: git checkout -b)
git switch main               # switch to existing branch
git branch -d feature/login   # delete merged branch
git branch -D feature/login   # force delete (unmerged work will be lost)
git branch -m new-name        # rename current branch

Merging

git switch main
git merge feature/login
  • Fast-forward merge: main has no new commits, so Git just moves the pointer. No merge commit.
  • Three-way merge: both branches have new commits, so Git creates a merge commit with two parents.
  • git merge --no-ff feature forces a merge commit even when fast-forward is possible (keeps feature history visible).
  • git merge --abort cancels a merge in progress.

6. Working with remotes

git remote -v                         # list remotes
git remote add origin <url>           # add a remote
git fetch                             # download new commits, do NOT change your files
git pull                              # fetch + merge (or rebase) into current branch
git push                              # upload commits on current branch
git push -u origin feature/login      # first push of a new branch; sets upstream
git push origin --delete feature/old  # delete a remote branch

fetch vs pull: fetch is safe, since it only updates your view of the remote (origin/main). pull = fetch + integrate into your current branch. When unsure, fetch first and inspect.

Never git push --force to a shared branch. If you must force after rewriting your own branch, use git push --force-with-lease, which refuses if someone else pushed in the meantime.

7. Resolving merge conflicts

A conflict happens when two branches change the same lines (or one deletes a file the other edited). Git pauses and marks the file:

<<<<<<< HEAD
your version (current branch)
=======
their version (incoming branch)
>>>>>>> feature/login

Steps:

  1. git status shows "both modified" files.
  2. Open each file, decide the final content, delete the <<<<<<<, =======, >>>>>>> markers.
  3. git add <file> to mark it resolved.
  4. git commit (or git merge --continue / git rebase --continue).

Tips:

  • VS Code shows "Accept Current / Incoming / Both" buttons.
  • Run the tests/app after resolving. A conflict-free file can still be logically broken.
  • To reduce conflicts: pull main often, keep branches short-lived, avoid mass reformatting.
  • git mergetool launches a configured visual tool.

8. Undoing things (the most important section)

Think about where the mistake is.

Situation Command
Discard edits to a file (not staged) git restore file.js
Unstage a file (keep edits) git restore --staged file.js
Fix the last commit message / add a forgotten file (not yet pushed) git add file; git commit --amend
Undo a commit but keep changes staged git reset --soft HEAD~1
Undo a commit, keep changes unstaged git reset HEAD~1 (mixed, default)
Undo a commit and DELETE the changes git reset --hard HEAD~1 (dangerous)
Undo a commit that is already pushed git revert <commit> (creates a new opposite commit, safe for shared history)
Delete untracked files git clean -n (dry run) then git clean -fd

Golden rule: reset rewrites history (only for local, unpushed commits). revert adds history (safe for pushed commits).

The safety net: reflog

git reflog lists everywhere HEAD has been, including commits you "lost" via reset or a deleted branch. Find the hash and run git reset --hard <hash> or git switch -c rescue <hash>. Committed work is almost never truly gone (for roughly 30-90 days by default). Uncommitted changes, however, cannot be recovered, so commit early.

9. Stash: park work temporarily

Use when you need to switch branches but are not ready to commit.

git stash                     # save tracked changes, clean working dir
git stash -u                  # include untracked files
git stash list
git stash pop                 # reapply latest stash and remove it
git stash apply               # reapply but keep it in the list
git stash drop stash@{0}
git stash push -m "wip login" # named stash

10. Rebase, cherry-pick, and history cleanup

Rebase

Replays your branch's commits on top of another branch, producing a linear history.

git switch feature/login
git rebase main               # move my commits on top of latest main
# conflicts? fix, git add, git rebase --continue   (or --abort)

Merge vs rebase:

  • Merge preserves exact history and is non-destructive, but is noisier.
  • Rebase gives a clean line, but rewrites commit hashes.
  • Never rebase commits that others have already pulled (public branches like main).

Interactive rebase (clean up before a PR)

git rebase -i HEAD~4          # squash, reword, reorder, drop the last 4 commits

Mark commits pick, squash/fixup (combine), reword, drop.

Cherry-pick

Copy one specific commit onto the current branch (e.g. a hotfix).

git cherry-pick <commit>

11. .gitignore

A file listing patterns Git should not track.

node_modules/
.env
*.log
dist/
build/
.vscode/
.DS_Store
__pycache__/
  • Never commit secrets (API keys, .env, passwords). If you do, deleting the file later does NOT remove it from history. Rotate the secret immediately and tell your team.
  • A file already tracked is not ignored retroactively: git rm --cached file then commit.
  • Commit a .env.example with fake values instead of the real .env.

12. Team workflows

Feature branch + pull request (what you will most likely use)

  1. git switch main && git pull
  2. git switch -c feature/short-description
  3. Work in small commits.
  4. git push -u origin feature/short-description
  5. Open a Pull Request (PR) on GitHub. Describe what and why, link the ticket, add screenshots for UI.
  6. Reviewers comment. You push more commits to the same branch and the PR updates.
  7. After approval, it is merged (merge commit, squash, or rebase, per team policy).
  8. Delete the branch, git switch main && git pull.

Branch naming

feature/login-page, fix/cart-total-bug, chore/update-deps, or with a ticket ID: feature/PROJ-123-login.

Branching strategies (know the names)

  • GitHub Flow: main is always deployable, short-lived feature branches, PRs. Simple and common.
  • GitFlow: long-lived main + develop, plus feature/*, release/*, hotfix/* branches. Heavier, suited to scheduled releases.
  • Trunk-based development: very short branches (or direct commits) to main with feature flags. Common with strong CI.

Code review etiquette

  • Keep PRs small (a few hundred lines at most).
  • Review your own diff before requesting review.
  • Respond to every comment, and don't take feedback personally.
  • Ensure tests/CI pass before asking for review.

Forks

Open-source flow: fork the repo, clone your fork, add the original as upstream (git remote add upstream <url>), sync with git fetch upstream, and open a PR from your fork.

13. Other useful tools

git tag v1.0.0                      # lightweight tag
git tag -a v1.0.0 -m "Release 1.0"  # annotated tag
git push origin v1.0.0              # push a tag (or --tags for all)

git bisect start                    # binary-search for the commit that introduced a bug
git bisect bad                      # current commit is broken
git bisect good <old-good-commit>   # then test, mark good/bad until found
git bisect reset

git restore --source=<commit> file  # restore a file from an older commit
git rm file.js                      # delete a file and stage the deletion
git mv old.js new.js                # rename and stage
git commit --amend --no-edit        # add staged changes to last commit, keep message

Aliases save typing:

git config --global alias.st status
git config --global alias.lg "log --oneline --graph --all --decorate"

14. Common mistakes and fixes

Mistake Fix
Committed on main by accident (not pushed) git branch feature/x (save the commit), then git reset --hard origin/main, then git switch feature/x
Wrong commit message (not pushed) git commit --amend -m "new message"
Committed a secret Rotate the secret first. Then clean history (git filter-repo or BFG) with your team's guidance.
"Your branch is behind origin" git pull
Push rejected (non-fast-forward) Someone pushed first. git pull (or git pull --rebase), resolve conflicts, push again.
Detached HEAD You checked out a commit, not a branch. git switch -c new-branch to keep your work.
Merge went wrong git merge --abort, or git reset --hard ORIG_HEAD right after
Deleted a branch by mistake git reflog, find its tip, git switch -c branch-name <hash>
Huge accidental file committed Remove it, add to .gitignore, and check repo size. Large files belong in Git LFS.
Line ending noise (Windows) git config --global core.autocrlf true (Windows) or input (Mac/Linux)

15. Habits that make you look good

  1. Run git status before every add/commit.
  2. Commit small and often. Push at least daily so work is backed up.
  3. Pull before you start work and before you push.
  4. Never commit directly to main if the team uses PRs.
  5. Read the diff (git diff --staged) before committing to catch debug logs and stray changes.
  6. Don't commit generated files, dependencies, or secrets.
  7. If you are scared of a command, make a backup branch first: git branch backup. It costs nothing.
  8. When stuck, don't panic-run commands. Run git status, git log --oneline --graph --all, and git reflog to understand the state.

17. Practice plan (when you have a laptop)

  1. Create a repo, make 5 commits, view with git log --oneline --graph.
  2. Make two branches editing the same line, merge, and resolve the conflict on purpose.
  3. Commit something wrong, then fix it with amend, reset, and revert (one each).
  4. Use git reflog to recover a deleted branch.
  5. Push to GitHub, open a PR on your own repo, and merge it.
  6. Interactive practice: learngitbranching.js.org. Reference book: Pro Git (free at git-scm.com/book).
